IMPORTANT DEVELOPMENT PRINCIPLES
================================

1. Use only synthetic data. Never use real customer or personal data.

2. Everything possible must be reproducible from source control.

3. Do not hardcode Salesforce record IDs.

4. Use external IDs for idempotent Salesforce upserts.

5. The pipeline must be rerunnable without producing duplicate records.

6. Keep Salesforce authentication outside source control.

7. Never commit:
   - Salesforce access tokens
   - passwords
   - security tokens
   - .env files
   - Power BI credentials

8. Prefer deterministic generation:
   random seed = 42.

9. Separate:
   - data generation
   - Salesforce integration
   - raw ingestion
   - quality detection
   - scoring
   - remediation
   - reporting

10. Every DQ finding must have:
    - rule ID
    - affected entity
    - quality dimension
    - severity
    - explanation
    - recommended remediation
    - detected timestamp
    - run ID

11. Do not automatically merge duplicate Salesforce records.
    Duplicate resolution must remain human-reviewed.

12. Safe deterministic fixes can be automated:
    - normalization
    - segmentation recalculation
    - standard formatting
    - missing derived fields

13. Every important business rule must be documented.

GROUND TRUTH EVALUATION
=======================

Because corruption was intentionally generated, evaluate duplicate and DQ
detection against ground_truth_issues.csv.

Calculate where possible:

precision
recall
true positives
false positives
false negatives

For deterministic quality rules expected precision should approach 1.0.

For fuzzy duplicates, document tradeoffs instead of optimizing to an artificial
perfect score.


DATA QUALITY SCORECARD
======================

Every quality dimension returns 0-100.

Dimension score:

100 * weighted_passed_checks / weighted_applicable_checks

Ignore non-applicable checks rather than counting them as passing.


OVERALL SCORE WEIGHTS
=====================

Use configurable weights:

Completeness: 0.25
Validity: 0.20
Uniqueness: 0.20
Consistency: 0.15
Hierarchy: 0.10
Enrichment: 0.10

Store weights in:

config/scoring.yml

Do not hardcode inside SQL where avoidable.


DQ STATUS
=========

Healthy:
score >= 90
and no Critical issue

Review:
score >= 70 and < 90
OR High-severity issue

Critical:
score < 70
OR any Critical issue

================

Calculate dollar value of OPEN Opportunities exposed to quality issues.

For Account-level issues:

Pipeline at Risk =
SUM of open Opportunity.Amount associated with the Account.

REMEDIATION PRIORITY
====================

Map severity:

Critical = 1.00
High     = 0.80
Medium   = 0.50
Low      = 0.25

Map segment importance:

Enterprise = 1.00
Mid-Market = 0.65
SMB        = 0.35

Normalize business impact using open pipeline.

Suggested:

impact_component =
min(
    1,
    ln(1 + pipeline_at_risk) / ln(1 + 1000000)
)

Priority formula:

priority_score =
100 * (
    0.40 * severity_component
  + 0.35 * impact_component
  + 0.15 * segment_component
  + 0.10 * detection_confidence
)

Round to two decimals.

This formula must be documented as a DEMO prioritization framework,
not presented as an industry standard.
